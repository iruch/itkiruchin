# Wallet API — тестовое задание ИТК Академия

REST-сервис для работы с кошельками: пополнение, списание и получение баланса.

## Стек

- Java 17
- Spring Boot 3.5 (Web, Data JPA, Validation)
- PostgreSQL 17
- Liquibase
- Docker / Docker Compose
- JUnit 5, MockMvc, Mockito
- Lombok

### Про версии

Сначала по привычке сгенерировал проект на Spring Boot 4.2 и JDK 25. Потом перечитал ТЗ (Java 8–17, Spring 3) и перевёл проект на Spring Boot 3.5 и Java 17. При переходе пришлось поправить `pom.xml`: в Spring Boot 4 стартеры разбиты на отдельные модули (`spring-boot-starter-webmvc`, `*-test` и т.д.), в 3.5 их нет. Также поменял несколько импортов в тестах.

## Эндпоинты

| Метод | URL | Описание |
|---|---|---|
| POST | `/api/v1/wallet` | Пополнение или списание |
| GET | `/api/v1/wallets/{walletId}` | Баланс кошелька |
| POST | `/api/v1/wallets` | Создать кошелёк с нулевым балансом |
| GET | `/api/v1/wallets` | Список всех кошельков с балансами |

Последних двух эндпоинтов в ТЗ нет. Я добавил их, потому что иначе непонятно, откуда брать кошелёк для проверки: без них пришлось бы вставлять его в базу руками.

### Пример операции

```http
POST /api/v1/wallet
Content-Type: application/json

{
  "walletId": "3f1c2a9e-8b7d-4c6e-9f10-2a3b4c5d6e7f",
  "operationType": "DEPOSIT",
  "amount": 1000
}
```

Ответ `200 OK`:

```json
{
  "walletId": "3f1c2a9e-8b7d-4c6e-9f10-2a3b4c5d6e7f",
  "balance": 1000.00
}
```

`operationType` — `DEPOSIT` (пополнение) или `WITHDRAW` (списание).
`amount` — больше 0, не больше двух знаков после запятой.

## Ошибки

Все ошибки возвращаются в одном формате:

```json
{
  "timestamp": "2026-11-10T09:00:00.000Z",
  "status": 409,
  "error": "Conflict",
  "message": "Недостаточно средств на кошельке: 3f1c2a9e-...",
  "path": "/api/v1/wallet"
}
```

| Ситуация | Статус |
|---|---|
| Кошелёк не найден | 404 |
| Недостаточно средств | 409 |
| Невалидный JSON, неизвестный `operationType`, невалидный UUID | 400 |
| Нет обязательного поля, сумма ≤ 0, больше 2 знаков после запятой | 400 |

Неизвестные исключения логируются со стектрейсом, а клиенту уходит 500 без подробностей, чтобы не светить внутренности.

## Как решена работа в конкурентной среде

Самое простое решение «прочитать баланс → посчитать в Java → сохранить» при параллельных запросах теряет обновления: два запроса читают одно и то же значение, и один перезаписывает результат другого.

Поэтому баланс меняется одним SQL-запросом:

```sql
UPDATE balances
SET amount = amount + :delta
WHERE wallet_uuid = :walletId AND amount + :delta >= 0
```

- PostgreSQL сам блокирует строку на время UPDATE, и запросы к одному кошельку выполняются по очереди. Обновления не теряются.
- Проверка «хватает ли денег» и списание происходят в одном запросе. Не может получиться так, что проверили, а пока списывали, денег уже не стало.
- Если запрос обновил 0 строк, значит, кошелька нет (404) или не хватает средств (409). Это обычные ответы, а не 500.
- Дополнительно в базе стоит `CHECK (amount >= 0)`, чтобы баланс не ушёл в минус, даже если в коде будет ошибка.

Тут не нужны ни повторы при конфликтах, ни блокировки в Java. Поэтому даже при большом количестве запросов на один кошелёк они не падают, а просто ждут своей очереди.

## База данных и миграции

Две таблицы:

- `wallets` — кошелёк (`uuid`, `created_at`)
- `balances` — баланс кошелька (`wallet_uuid`, `amount NUMERIC(19,2)`, `version`), связь один к одному с `wallets`

Деньги хранятся в `NUMERIC(19,2)`, в Java это `BigDecimal`. `double` для денег не подходит из-за ошибок округления.

Миграции лежат в `src/main/resources/db/changelog`: master-файл подключает изменения из папки `changes` по порядку.

С Liquibase я раньше не работал, до этого плотно работал с Flyway. Пришлось разобраться со структурой changelog'ов, форматом changeset'ов и тем, как Liquibase хранит историю в `databasechangelog`. Подход в целом такой же, как во Flyway (версионированные миграции, которые нельзя менять после применения), так что это не стало проблемой.

## Настройка без пересборки

- Параметры БД (имя базы, пользователь, пароль) лежат в `.env` и подставляются в `compose.yaml`. Используются и контейнером PostgreSQL, и приложением.
- Параметры приложения передаются через переменные окружения в `compose.yaml` (секция `environment` у сервиса `app`). Spring Boot умеет переопределять любое свойство из `application.yaml` переменной окружения, например:
    - `SERVER_PORT=8081`
    - `SPRING_DATASOURCE_HIKARI_MAXIMUM_POOL_SIZE=20`

Чтобы применить изменения, достаточно поменять `.env` или `compose.yaml` и выполнить `docker compose --profile full up -d`. Образ при этом не пересобирается, пересоздаются только контейнеры.

## compose.yaml

| Сервис | Профиль | Что делает |
|---|---|---|
| `postgres` | — (всегда) | PostgreSQL 17, данные хранятся в volume `pgdata` |
| `liquibase` | `full` | Накатывает миграции и завершается |
| `app` | `full` | Приложение, стартует только после успешных миграций |

Порядок запуска в полном режиме: `postgres` (ждём healthcheck) → `liquibase` → `app`.

Зачем профиль `full`: в проекте подключён `spring-boot-docker-compose`. При запуске приложения из IDE Spring сам выполняет `docker compose up` для `compose.yaml`. Без профиля он поднял бы и `app` (вторую копию приложения, конфликт по порту 8080), и `liquibase` (миграции накатывались бы дважды). Сервисы с профилем `full` Spring не трогает, поэтому при запуске из IDE поднимается только база.

## Запуск

### Подготовка (обязательно)

```bash
cp .env.example .env
```

На Windows в cmd: `copy .env.example .env`.

Без `.env` контейнер PostgreSQL не стартует: у него не будет пароля.

### Вариант 1. Из IDE

Нужно: Java 17 и запущенный Docker Desktop.

1. Открыть проект в IntelliJ IDEA.
2. Запустить `TestApplication`.

При старте:

- Spring сам поднимет контейнер `postgres` из `compose.yaml` и подключится к нему (порт подставляется автоматически).
- Liquibase внутри приложения накатит миграции.
- Приложение будет доступно на `http://localhost:8080`.

### Вариант 2. Всё в Docker

```bash
docker compose --profile full up -d --build
```

Поднимутся `postgres`, `liquibase` и `app`. Приложение будет доступно на `http://localhost:8080`.

Логи:

```bash
docker compose logs -f app
docker compose logs liquibase
```

Остановка:

```bash
docker compose --profile full down       # остановить
docker compose --profile full down -v    # остановить и удалить данные БД
```

### Подключиться к базе

```bash
docker exec -it postgres psql -U app -d appdb
```

PostgreSQL наружу пробрасывается на случайный порт. Узнать его, например для DBeaver:

```bash
docker compose port postgres 5432
```

## Тесты

```bash
./mvnw test
```

На Windows: `mvnw.cmd test`.

Тесты в `WalletControllerTest` написаны на `@WebMvcTest` + MockMvc, сервис замокан через `@MockitoBean`. Проверяется каждый эндпоинт: успешные ответы, 404, 409 и 400 при невалидных данных и кривом JSON. Docker и база для тестов не нужны.

Импорт: Postman → Import → выбрать файл. Сначала выполнить запрос создания кошелька, его `walletId` подставится в остальные запросы.
